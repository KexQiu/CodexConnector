# Codex 多版本兼容策略

更新日期：2026-09-28。

## 已实现的版本门禁

编译协议与运行版本解耦：`src/runtime-baseline.json` / `src/codex/generated` 继续固定于 `0.155.0-alpha.9.2`，作为网关适配器的稳定开发接口。运行时不再用版本字符串全等决定兼容性，也不简单放开整个 `0.x` 或 alpha 范围。

`src/codex/compatibility-profile.json` 保存网关实际依赖的协议契约。每次检查或启动，调用所选程序的 `--version` 和 `app-server generate-json-schema --experimental`，与该契约做有方向的比较。生成过程使用临时独立 CODEX_HOME，不连接 RPC、不登录、不触发模型任务或飞书消息，完成后清理。版本命令最长 5 秒、导出最长 15 秒、文件最多 16 MiB，失败不会绕过检查。检查前后版本不一致也要求重试；不长期缓存成功结果。

| 检查结果                           | 是否可以启动 | 对用户的含义                                                                                                     |
| ---------------------------------- | ------------ | ---------------------------------------------------------------------------------------------------------------- |
| 已验证版本，协议通过               | 可以         | 有对应真实验收记录，仍检查当前二进制实际契约                                                                     |
| 核心协议兼容，版本未完整联调       | 可以         | 保持现有权限、响应校验、执行锁和恢复保护；不等同该版本所有行为都已验收                                           |
| 核心协议不兼容                     | 阻止         | 展示发生变化的方法或字段，需升级适配器                                                                           |
| 程序缺失、不可执行、协议导出失败   | 阻止         | 展示对应原因，不再笼统归为版本号不匹配                                                                           |
| Node 不符合支持范围或原生 API 下限 | 阻止         | 支持 Node 22.14+（22.x）/ 24.x 和 Node-API 10；App 内置版本单独固定，见 [Node 兼容策略](./NODE_COMPATIBILITY.md) |

当前有一个适配器配置 `gateway-v1`：捕获的 `0.155.0-alpha.9.2`、`0.155.1` 与 `0.158.0-alpha.2.1` 协议快照都可使用。`0.158.0-alpha.2.1` 的基础本地 RPC 检查已通过；真实任务、审批、取消、恢复和账号行为没有因此自动升级为“已验证”。验证等级由 `src/codex/compatibility.ts` 中明确记录的版本控制。已知存在语义回归的版本可加入同文件的禁止列表，即使 schema 相同也不能启动。

## 哪些差异自动接受

- 网关未调用的新增 RPC 方法、未订阅的新通知、无关插件/语音类型。
- 普通请求增加可选字段，普通响应增加字段。
- 文档注释、字段顺序等非契约变化。
- 大型配置对象只比较网关消费的模型与配置要求字段；动态 `features` / `mcp_servers` 仍在真实 `config/read` 中回读验证。

以下变化保守拦截：所需方法或字段删除；请求新增必填项；响应不再保证必要字段；类型、枚举、联合类型或约束改变；沙箱/权限/审批结构改变。即便某个联合扩展理论上可忽略，也需要人工确认当前消费者的处理方式，不猜测安全。

检查不是通用 JSON Schema 子类型证明器，也不能识别“字段没变、行为变了”。当前方案按既有生成器的结构比较，遇到无法解释的结构失败关闭。安全相关结构不使用普通“忽略新增字段”规则。网关原有运行时响应校验、有效权限回读、未知交互拒绝、unknown 恢复与防重复执行逻辑继续生效。

这份契约不覆盖 Codex 私有磁盘布局（项目登记表、rollout token 使用量等）的长期稳定性；读取异常沿用现有降级，不改写 Codex 数据。相应格式变化仍须独立验证适配。

## 安装路径变更

自动发现 `/Applications` 与 `~/Applications` 下 ChatGPT.app / Codex.app 的两种布局：

- `Contents/Resources/codex`
- `Contents/Resources/codex-cli/bin/codex`

缓存旧入口不存在时，只尝试同一应用包的新入口。不会把手动指定的失效自定义 CLI 静默切换到另一安装。新入口会显示在界面，后续应用配置时保存；不修改凭据、项目权限或数据档案。现有 CLI LaunchAgent 清单仍要求路径一致；若其路径变化，需停止后显式更新部署清单，不能偷偷切换常驻服务。

## 开发者检查命令

```sh
# 自动发现本机 Codex；可用于任意候选版本，失败退出码为 1
pnpm protocol:compatibility

# 检查指定版本安装，带空格的路径必须加引号
pnpm protocol:compatibility --binary '/Applications/ChatGPT.app/Contents/Resources/codex-cli/bin/codex'

# 确认运行契约与受版本控制的基线 schema 一致
pnpm protocol:profile --check
```

`protocol:generate` / `protocol:check` 继续只允许生成基线版本，防止本机自动更新后无意覆盖整套开发类型。检查候选版本请用 `protocol:compatibility`，不要先修改基线号。`protocol:profile` 用于有意调整契约；它不是“让不兼容版本通过”的快捷开关。

## 后续版本迭代流程

1. **保存候选证据。** 记录版本、入口、导出 schema、哈希、平台与架构；保留旧 schema 和真实验收报告。候选原始 schema 置于 `schemas/codex/<version>/protocol.schema.json`。
2. **先检查差异。** `protocol:compatibility` 通过时，现有适配器即可连接，界面仍注明未完整联调；没有必要仅为版本号变化发布 App。
3. **契约变化时集中适配。** 在 Codex 边界转换新旧请求/响应为网关稳定领域对象，不让版本判断散入飞书卡片、任务状态机或数据库。不把安全字段缺失解释成允许。当前仅有 `gateway-v1`；确有破坏性升级时才增加 `gateway-v2`，保留旧适配器与旧测试，不直接覆盖旧类型后宣布向后兼容。
4. **执行双版本回归。** 旧版本和候选版本分别跑契约检查、编译及自动化。真实验收至少覆盖新建/续聊、排队、中断、审批与输入、只读/写入/联网边界、断线恢复、unknown 不重放、App 退出不影响桌面任务、额度与上下文。
5. **提升验证等级。** 只有对应版本真实验收完成，才加入已验证版本集合并链接验收证据；发现 schema 无变化的语义回归时先加入禁止列表，修复后再恢复支持。
6. **发布与回退。** 使用独立 desktop 构建目录生成新 App；协议升级本身不应要求网关数据库迁移。用户可继续选择兼容的旧 Codex 安装；需要数据迁移时另做备份与回退评估。

## 后续可扩展项

- 将额度、模型展示等可选能力从核心契约拆成独立能力组：单个可选接口变化只关闭对应展示，不能影响创建、恢复、权限和中断等核心能力。目前统一保守校验，尚未实现按组关闭。
- 有第二种实际不兼容协议后，再增加适配器路由与显式支持周期。
- 在 CI 提供多个 Codex 二进制版本的本地协议与实际任务矩阵；目前仓库自动化覆盖保存的三个 schema，真实历史版本二进制仍需对应环境执行。

官方依据：[OpenAI Docs — Codex App Server](https://learn.chatgpt.com/docs/app-server)。导出的 schema 对应实际运行的 Codex 版本；实验接口显式 opt-in。具体兼容结论以捕获的 schema、自动化及各版本真实验收为准。
