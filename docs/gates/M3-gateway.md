## 本机配置和启动

已准备被忽略的 `config/gateway.local.json`，权限 600。它只引用 `config/feishu.local.json` 的凭据文件路径，不复制 App Secret。当前项目登记为只读；正式远程执行前，在该文件中为明确允许执行的项目开启 `remoteWrite`。一次只在一个进程中使用这套飞书应用，不同时运行 G1 探针、M3 探针和正式 Gateway。

`feishu.local.json` 中的 `testChatId` 在 M3 作为唯一允许收发的单聊。Gateway 配置中的 appId/tenantKey/allowedOpenId 必须与凭据一致；不接受群聊或任意新 chat_id。

先在飞书开放平台的该应用中检查：机器人能力、允许用户的可用范围、消息接收事件 `im.message.receive_v1`、卡片回调 `card.action.trigger`、发送/更新消息所需权限，以及 `im:message.history:readonly`。按后台要求发布/审批使变更生效。已有 G1 订阅不需要重复添加。

在项目根目录的两个终端中分别运行：

```sh
# 终端一：独立 App Server；不要删除正在监听的 socket
umask 077
mkdir -p "$PWD/.artifacts/gateway-local"
chmod 700 "$PWD/.artifacts/gateway-local"
/Applications/ChatGPT.app/Contents/Resources/codex app-server \
  --listen "unix://$PWD/.artifacts/gateway-local/app-server.sock" -c 'notify=[]'

# 终端二：前台 Gateway
export CODEX_FEISHU_CONFIG="$PWD/config/gateway.local.json"
pnpm config:check
pnpm dev gateway
# 可选有界运行：pnpm dev gateway --timeout 900
```

使用其他 dataDir 时，配置里的 endpoint 和 App Server 的 socket 参数必须一致。`gateway` 不安装 LaunchAgent；Control+C 关闭 Gateway 自己的连接，App Server 保持由原终端管理。未确定结果的任务保留锁，重启通过已知 turn 核对。

卡片按钮需要接收回调的 Gateway 长连接在线。`gate:gateway` 是有运行时限的临时验收进程，测试结束或超时会关闭连接；飞书里的旧卡片仍然可见，不代表回调服务仍在线。遇到“目标回调服务未在线”时，先检查进程和该轮报告。新探针有独立数据库和前缀，直接启动新探针不能接管旧卡片；需要恢复原记录并更新动作，或使用新一轮卡片重新测试。日常持续可用需完成 M5 常驻部署。

短 ID 至少 8 位且必须唯一。普通文本没有明确项目/会话时会提示选择，不猜执行目标。拒绝命令也会生成持久化提示；暂时的命令处理错误最多自动尝试 5 次，之后保留 failed 等待本机核对。

“回复卡片”指飞书的引用回复操作：长按目标卡片并选择“回复”，确认输入框上方出现引用后再发送。直接在聊天输入框粘贴会使用已选择的任务/项目，不会因刚点过另一张卡片的“刷新状态”就切换会话。

卡片展示任务、项目、目录、thread/turn、状态、耗时及有界结果摘要。completed 仅表示模型结束，仍需验收需求。M3 没有文件变更汇总或流式输出；完整结果可在本机用 `task --result` 读取。

## 消息与通知故障恢复

若用户发出的指令因入站存储失败未被确认，不假定平台一定自动重投。先恢复磁盘/数据库连接，再按该条消息 ID 补收：

```sh
pnpm dev feishu-recover-message --message-id om_MESSAGE_ID
pnpm dev gateway
```

补收通过飞书 API 获取消息，只接受配置单聊中该用户的未删除文本消息；原消息业务键不变，已处理的指令不会再执行，已失败的命令恢复重试资格。该入口只入队，任务实际派发由 Gateway 完成。不要通过重新发送任务正文绕过去重。

发送前将完整卡片内容、回执标记和动作 nonce 固定到 outbox。标题同时保存回执，使飞书只返回预览时仍能核对。明确限流按响应等待时间及退避重试；永久权限/参数拒绝记 failed；网络断开、超时、5xx 或缺少回执记 unknown。新卡 unknown 通过限界历史查询匹配回执，PATCH unknown 读取原 message_id；只认可同应用、同单聊且唯一匹配的消息。每项核对间隔 30 秒，最多读取 500 条；分页总预算 20 秒，单请求超时 10 秒，截断不是未发送证据。

回执字段是本项目的关联标记，不是飞书服务端幂等保证。即使发送请求携带 uuid，当前实现也不会在 unknown 时盲目重发。消息被删除、永久失败后的重建和人工解除 unknown 尚未提供自动入口。`state` / `doctor --config` 可查看 outbox 错误分类与命令失败统计。

共享 Codex Home 时，桌面应用可能加载 Gateway 创建的会话。同一会话被其他 App Server 占用时，独立 Gateway 的恢复请求会被拒绝，不能因为没有新 turn 就强制删除写锁或终止别的进程。当前保留 failed 并提示在本机协调占用；跨进程交接已在后续 [M4 验收](./M4-interactions.md) 中补齐。只读历史查询与加载会话不同，官方 [App Server 文档](https://learn.chatgpt.com/docs/app-server) 说明 `thread/read` 不加载会话，而 `thread/resume` 会恢复会话；具体写锁冲突结论来自本机固定版本日志和持锁进程检查。

SDK 的高层 Channel 重试和错误映射没有直接用于此链路；使用官方 WSClient/EventDispatcher 收事件，固定域名 HTTP 适配器发送/读取，确保一次变更尝试只对应一个持久化发送阶段。已安装 SDK 的高层分类把 `99991400` 视为权限错误；这里按官方频控定义处理，并有 HTTP/业务码测试。

## 升级与复测

升级 v1 数据前停止旧 worker、备份，再启动新入口。`db-backup` 在构造 TaskStore/执行迁移之前调用 SQLite backup API，不会先升级再备份；目标必须为新的私有路径。原 `001_tasks.sql` 保持不变，新增 `002_feishu.sql` 并校验每一步 checksum。迁移失败整个事务回滚。

```sh
pnpm dev db-backup --destination /absolute/private/backups/pre-m3.sqlite
pnpm run doctor --config "$CODEX_FEISHU_CONFIG"
pnpm verify
pnpm gate:gateway --live --timeout 900
```

旧 v1 库在迁移前由新 doctor 显示不兼容，这是预期保护；新任务/Gateway 入口会在没有旧 worker 的情况下执行迁移。M3 成功后不能直接用旧 M2 程序写 v2 数据库。

真实探针就绪后输出本轮前缀和两条新建命令。手机连续发送两条，等待卡片完成，再按提示在第一张卡片点击刷新两次并回复它续跑。探针故意丢弃第一次真实 POST 的成功回包，要求查询回执恢复原卡，而不是新增消息。最终检查 3 次 turn/start、正确会话归属、终态卡片、无重复 POST 和锁释放。平台自动重投仍属 G1 未覆盖项，不会因本地重放通过而改成 PASS。
